---
title: "Back up, export and erase"
description: "One archive holds the vault key and the database, because neither restores without the other; the export is data only, and erase is permanent."
---

<Info>
  **Before you start**

  - **A terminal on the machine Postern runs on.** Every command here runs from the directory
    holding `docker-compose.yml` and `.env`. The Console cannot take a backup: Settings → Your data
    has a **Back up now** row, and its button is disabled, because backup runs on the box and its
    status is not served to the Console.
  - **Postern already installed and running.** [Install Postern](/start/install) if it is not.
  - **How long: mostly the database dump.** The commands are short. The dump takes as long as the
    data it is copying, and the restore takes as long as loading it back.
  - **Two things that are useless apart** — the master key, which opens the sealed vault, and the
    Postgres database, which holds the sealed rows along with every connector, grant and cached
    record. The key without the database decrypts nothing. The database without the key is an opaque
    blob. A backup is one archive holding both.
  - **Which custody your key is in decides the first step.** If you never set `PCI_MASTER_KEY`, the
    gateway generated a key and keeps it in a Docker volume. If you did set it, that value is the
    key and there is nothing in the volume to capture.
  - **The archive is a plaintext-equivalent secret.** It carries the key that opens every credential
    inside it. Mode `0600`, kept off the box, treated exactly like the credentials it contains.
  - **The export is not a backup.** It is a JSON copy of the cached data. It carries no credentials,
    and there is no route that reads one back in.
  - **Erase is a hard delete.** The rows are gone, the export cannot put them back, and repopulating
    means reconnecting and re-syncing from the source.
  - **Nothing here is scheduled.** Postern ships no scheduler and no remote target. When a backup
    runs, and where the copy goes, are yours to arrange.
</Info>

## Choose your path

Three jobs live on this page, and they are not a sequence. Take the row you came for.

| If you want to… | Then |
|---|---|
| protect yourself against losing this machine | [Check where your vault key lives](#check-where-your-vault-key-lives), then work down to the archive |
| move Postern to another machine, or recover from a lost one | [Unpack the archive on the new machine](#unpack-the-archive-on-the-new-machine) |
| read your cached data somewhere else, or keep a copy you can open | [Export everything as one JSON file](#export-everything-as-one-json-file) |
| destroy cached data — one connection, one sector, or all of it | [Choose what to erase and take the export first](#choose-what-to-erase-and-take-the-export-first) |

<Steps>

<Step title="Check where your vault key lives" titleSize="h2" id="key-custody">

In the directory holding `docker-compose.yml`, look for a self-managed key in `.env`:

```bash
grep -c '^PCI_MASTER_KEY=' .env
```

It prints `0` when `.env` carries no such line. That is the default, and the case the rest of this
page assumes: the gateway generated a 32-byte key on first boot and persists it at
`/app/.pci/master.key` inside the named volume `pci_master_key`. **The volume is the key.**

It prints `1` when the line is there, and then what follows the `=` decides. An empty
`PCI_MASTER_KEY=` counts as unset — the gateway reads an empty value as no value — and leaves you in
the gateway-managed case above. A real base64 value means you manage the key yourself, and there is
nothing in the volume to capture: the key is that value, and backing it up means storing it out of
band, in a password manager, not beside the dump. Skip the next two steps and the key-seeding step
on restore; make sure `PCI_MASTER_KEY` — and `PCI_MASTER_KEY_ID`, if you set one — are in `.env`
before the gateway's first boot on the new machine.

<Note>
  The repository ships `scripts/backup.sh`, which does the key capture, the dump and the archive in
  one command. It reads the key from a host path, `.pci/master.key` by default. On the shipped
  Docker layout no such file exists — the key is inside the volume — so it exits with
  `refusing a keyless backup` rather than writing an archive. Take the steps below instead. Under
  self-managed custody it writes a note recording that the key was env-managed, and you still have
  to archive that value yourself.
</Note>

</Step>

<Step title="Copy the key out of the running container" titleSize="h2" id="capture-key">

<Warning>
  Take the key from the container or from the volume, never from your checkout. A directory may hold
  a host-side `./.pci/master.key` from a non-Docker run, or you may create one by hand expecting it
  to be read. It is a **different key**. Paired with a dump taken from the container it produces an
  archive that unpacks and restores cleanly and then cannot open a single credential — and the
  gateway will refuse to boot rather than start green, which is the loud version of a failure that
  used to be silent. The boot check is deliberately narrow, so a real read is still the verification
  that counts.
</Warning>

With the stack up, stage the key and check what you captured. `wc -c` printing `32` is the whole
test: anything else means you captured something other than the key.

```bash
mkdir -p ./backup-staging && chmod 700 ./backup-staging
docker compose exec -T app cat /app/.pci/master.key > ./backup-staging/master.key
chmod 600 ./backup-staging/master.key
```

```bash
wc -c < ./backup-staging/master.key
shasum -a 256 ./backup-staging/master.key
```

Note the checksum down. You check it again at restore time, and it is what proves a key and a dump
came out of the same archive.

</Step>

<Step title="Read the key from the volume when the app is stopped" titleSize="h2" id="capture-key-stopped">

If the app container is not running — including after a boot refusal — the same bytes are in the
volume and need no running container. Docker prefixes the volume name with your project directory,
so resolve the real name first, then read through a throwaway container:

```bash
KEYVOL=$(docker inspect -f '{{range .Mounts}}{{if eq .Destination "/app/.pci"}}{{.Name}}{{end}}{{end}}' \
  "$(docker compose ps -aq app)")

docker run --rm -v "$KEYVOL":/k alpine cat /k/master.key > ./backup-staging/master.key
```

`echo "$KEYVOL"` prints something ending in `_pci_master_key`. The same resolution is used on
restore and by the key-rotation procedure, so it is worth recognising.

</Step>

<Step title="Dump the database" titleSize="h2" id="dump-database">

Dump Postgres in its custom format, which is what `pg_restore` reads. The gateway can stay up for
this; for a fully consistent snapshot, quiesce it first with `docker compose stop app` and leave the
database running, so nothing can be re-sealed or refreshed underneath you.

```bash
docker compose exec -T db pg_dump -U pci -d pci -Fc > ./backup-staging/pci.dump
```

`./backup-staging` now holds both halves. Substitute your own values if you changed `POSTGRES_USER`
or `POSTGRES_DB` in `.env`. No password is needed: the command runs inside the database container
and connects over its local socket, which is also why this goes through `docker compose exec`
rather than a `psql -h localhost` — the database service publishes no host port.

</Step>

<Step title="Pack both halves into one archive" titleSize="h2" id="archive">

Put the key and the dump in a single tarball, lock it down, and drop the staging directory:

```bash
tar -czf "postern-backup-$(date -u +%Y%m%dT%H%M%SZ).tar.gz" -C ./backup-staging .
chmod 600 postern-backup-*.tar.gz
rm -rf ./backup-staging
```

The archive holds two files, and it is a backup only while it holds both:

```text
master.key    32 raw bytes  (absent under self-managed custody — that value lives in your .env)
pci.dump      pg_dump -Fc
```

Copy it somewhere else now. A backup that only exists on the machine you are protecting is not a
backup, and it is a plaintext-equivalent secret in transit as well as at rest.

<Note>
  Rotating the master key re-seals every row under a new key, so a rotation and a backup can drift
  apart in exactly one way: never rotate between capturing the key and taking the dump, and always
  take a fresh backup immediately before rotating. After a rotation the older dump is sealed under
  the old key — restoring it needs that old key, and restoring the new key against an old dump fails
  closed. Keep the pre-rotation archive until every connection is green again. The rotation
  procedure itself is `docs/runbooks/key-rotation.md` in the repository.
</Note>

The gateway prints a `VAULT KEY IS NOT BACKED UP` banner to its log on every boot until the copy is
acknowledged, and the acknowledgement is a marker file written beside the key inside the volume.
Nothing in the Console writes that marker today, so on a gateway-managed key the banner keeps
printing after you have taken a perfectly good backup. It is a reminder rather than an error, and
nothing else about the gateway's behaviour depends on it.

</Step>

<Step title="Unpack the archive on the new machine" titleSize="h2" id="restore-unpack">

On the target machine, in an empty directory, put `docker-compose.yml` and a `.env` carrying at
minimum `POSTGRES_PASSWORD` — Compose refuses to start without it — plus any other variables you had
set. Do not start the stack yet. Then unpack the archive somewhere private and check the key against
what you recorded:

```bash
mkdir -p ./restore && chmod 700 ./restore
tar -xzf postern-backup-<stamp>.tar.gz -C ./restore
wc -c < ./restore/master.key
shasum -a 256 ./restore/master.key
```

`wc -c` prints `32` and the checksum equals the one you noted at backup time. A checksum that does
not match means these two halves are from different points in time, and the restore will fail
closed at boot rather than half-work.

</Step>

<Step title="Put the key in the volume before the first boot" titleSize="h2" id="restore-key">

The order matters, because boot is what opens the vault: the key has to be in the volume before the
gateway starts for the first time. Bring up Postgres, then create the app container without starting
it — creating the container is what materialises the `pci_master_key` volume, so there is somewhere
to put the key:

```bash
docker compose up -d db
docker compose create app
```

Wait until `docker compose ps` reports the database healthy. Then resolve the volume's real name and
pipe the key in:

```bash
KEYVOL=$(docker inspect -f '{{range .Mounts}}{{if eq .Destination "/app/.pci"}}{{.Name}}{{end}}{{end}}' \
  "$(docker compose ps -aq app)")

docker run --rm -i -v "$KEYVOL":/k alpine \
  sh -c 'cat > /k/master.key && chmod 600 /k/master.key && chown 1000:1000 /k/master.key' \
  < ./restore/master.key
```

`1000:1000` is the `node` user the image runs as, and the gateway cannot read a key it does not own.
Piping through stdin keeps the key off any host bind-mount. Under self-managed custody skip this
step entirely: set `PCI_MASTER_KEY`, and `PCI_MASTER_KEY_ID` if you used one, in `.env` instead.

</Step>

<Step title="Restore the database" titleSize="h2" id="restore-database">

<Warning>
  On a genuinely fresh machine the database is already empty and the `pg_restore` line alone is
  enough. The two lines above it drop and recreate the database, so that the dump lands on an empty
  schema — run them only when you are restoring **over** an existing Postern, and understand that
  they destroy what is there. Nothing about that is recoverable except from another archive.
</Warning>

```bash
docker compose exec -T db dropdb   -U pci --if-exists pci </dev/null
docker compose exec -T db createdb -U pci pci </dev/null
docker compose exec -T db pg_restore -U pci -d pci --no-owner < ./restore/pci.dump
```

`pg_restore` finishes without naming a failed item, and the database now holds every sealed row the
dump carried.

<Note>
  `docker compose exec -T` reads standard input, so a command in that form that does not need stdin
  will swallow the rest of a script you piped in, silently truncating everything after it. Give
  every such command an explicit `</dev/null`, exactly as above, and run a multi-step restore from a
  saved script file rather than a heredoc.
</Note>

</Step>

<Step title="Start the gateway and open a real secret" titleSize="h2" id="restore-verify">

Start the app. Its migrations run inside boot and see an already-current schema, so they are a
no-op, and the vault check runs before any edge serves:

```bash
docker compose up -d app
docker compose logs app | grep -iE 'SecretAuth|MasterKey'
curl -fsS http://localhost:8787/healthz
```

Give it a moment before the curl: the migrations and the vault check both run inside boot, and the
edge does not bind its port until they are done. The log grep then prints nothing and `/healthz`
answers `{"status":"ok"}`. That says the gateway is up and its database is reachable. It does not
say the key matches the vault. Force a real secret open:
in the Console, pick a connection and sync it now. A sync opens that connection's sealed credential,
and every connection returning to `ok` is the only end-to-end proof that the key and the dump belong
together. Delete `./restore` once you have that; keep the archive.

<Note>
  A `SecretAuthError` or `MasterKeyError` in the log — or a refusal to start naming a `key_id` it
  cannot open — means the key and the dump are from different points in time. Check
  `PCI_MASTER_KEY_ID` first: rows are looked up by that label, so the key can be perfectly fine and
  only its label diverged, in which case nothing needs restoring. Otherwise re-capture the key from
  the source machine's running container and restore again. If the source machine is gone and the
  key went with it, the data is not recoverable, which is why the two travel in one archive.
</Note>

</Step>

<Step title="Export everything as one JSON file" titleSize="h2" id="export">

In the Console, Settings → Your data → **Export everything** → **Export** downloads one file named
`postern-export-<date>.json`. The same bundle is a plain GET, which you can run on the box or
through the same SSH tunnel that brings you the Console — the route answers on loopback only,
because the bundle is the whole store and is not narrowed by any agent's grant:

```bash
curl -fsS http://localhost:8787/api/export -o postern-export.json
```

The file holds a `manifest` and a `data` object. The manifest carries the export timestamp, the
sectors that actually had rows, a per-object row count, and an inventory of your connections —
connection id, provider, sector, status and last sync time. `data` is keyed by object —
`finance.transaction`, `health.workout`, and for the sectors that hold a single object the sector's
own name, `mail`, `calendar`, `contacts`, `home` — and holds every live row in full, including the
`raw` payload the source returned. Rows the source itself has removed are not in it: they are gone
at the source, not your data.

What is **not** in it is as load-bearing as what is. No credentials, no tokens, no access URLs —
those stay sealed in the database, which is why an export is not something you can restore from, and
why there is no route that reads one back in. Restoring a gateway is the archive above; undoing an
erase is reconnecting the source and syncing again.

Appending `?sector=finance` narrows the bundle to one sector's tables. A sector name the gateway
does not know is a `400` answering `unknown sector: <name>`, and the six it knows are `finance`,
`mail`, `calendar`, `contacts`, `health` and `home`. Either way one row lands in Console → The
ledger under the tool `export`, carrying the sector if you narrowed it and the number of rows, never
the rows themselves.

</Step>

<Step title="Choose what to erase and take the export first" titleSize="h2" id="erase-scope">

<Warning>
  Erase is a hard delete of the rows themselves, not a mark that the next sync undoes. There is no
  undo and no import: the export you take here is a copy you can read, not a copy the gateway can
  read back. The only thing that reverses an erase is reconnecting the source and syncing it again —
  and for a Plaid connection not even that, because the erase removes the Item upstream and a new
  Link has to be created.
</Warning>

In the Console, Settings → Your data → **Erase…** opens its own page. Pick a scope, and it states
exactly what that scope reaches before anything happens:

- **One connection** — that source's cached rows only. It stays connected and a re-sync repopulates
  it.
- **A sector** — everything in one sector across every provider. The connections stay connected.
- **Everything** — every sector, every connection. The gateway keeps its identity and your agent
  keys; the data is gone.

The least destructive scope is selected first, and the export is enforced rather than offered: the
confirm button stays disabled until the export has actually been taken, and you type `ERASE` to arm
it. Changing the target after arming re-closes both guards, so escalating from one connection to
everything makes you take the export and type the word again.

What survives an erase, whatever the scope: the connector and credential rows, so you can re-sync
without reconnecting from scratch, and the audit ledger, which records that the erase happened and
never held the row values. Erase is not disconnect and it is not revoke; the three are separate
acts.

<Note>
  On a Plaid connection, Postern calls Plaid's `/item/remove` for every matching Item before any row
  is deleted, which also stops the paid subscription those Items are billed under, and then marks
  the kept credential dead. That is deliberate: `/item/remove` invalidates the access token
  upstream, so a later re-sync cannot resume — it needs a brand-new Link rather than an update.
  Every other provider's credential survives the erase and re-syncs as it is. The billing stop is
  best-effort and never blocks the erase, so a hiccup there can leave an Item live at Plaid; check
  it there if the subscription matters to you.
</Note>

</Step>

<Step title="Send the erase with the token the gateway expects" titleSize="h2" id="erase-send">

<Note>
  The word the Console asks you to type and the token the gateway checks are not the same string.
  The Console types `ERASE` for every scope; the gateway checks the name of the thing being erased.
  If an erase fails naming `confirmation token does not match the requested scope`, nothing was
  deleted — the token is checked before any row is touched — and the erase below is the form that
  goes through.
</Note>

Run this on the box, or through the same tunnel you use for the Console. The token the gateway
expects is the thing you named: for one connection it is that connection's id, for a sector it is
the sector name, and for everything it is the literal `ERASE-ALL`.

```bash
curl -fsS -X POST http://localhost:8787/api/erase \
  -H 'content-type: application/json' \
  -d '{"scope":"connection","connectionId":"<connection-id>","confirm":"<connection-id>"}'
```

It answers with the scope, a per-table count of the rows deleted, and the total. Tables that lost
nothing are omitted, so a short answer on a machine holding a lot of data usually means you named a
narrower scope than you meant. A connection id that is not yours, or is not a connection id at all,
is a `404` and
deletes nothing. `<connection-id>` comes from the picker on the Console's erase page, which shows
each connection's first characters, or in full from `manifest.connections` in the export you just
took.

The deletes run as independent statements rather than one transaction, and a delete is idempotent —
so an erase that fails partway through is fully recovered by running the same command again.

</Step>

</Steps>

## Confirm it works

These are the checks that catch the failures you cannot see: a key that is not the key, two halves
from different points in time, and a restore that boots without being able to read anything. Run the
first two while the staging directory still exists, before you pack the archive — or against
`./restore/master.key` after unpacking on the other machine. Run the last two after a restore.

```bash
wc -c < ./backup-staging/master.key
shasum -a 256 ./backup-staging/master.key
docker compose logs app | grep -iE 'SecretAuth|MasterKey'
curl -fsS http://localhost:8787/healthz
```

- `wc -c` prints exactly `32`. Anything else means you captured something other than the key, and
  the archive is worth nothing until you capture it again.
- The checksum you recorded at backup time equals the one you compute after unpacking. Restore a key
  and a dump only from the same archive.
- The archive holds both `master.key` and `pci.dump` — or, under self-managed custody, holds the
  dump and you can produce the `PCI_MASTER_KEY` value from wherever you stored it.
- After a restore, the log grep prints nothing and `curl -fsS http://localhost:8787/healthz` answers
  `{"status":"ok"}`.
- A connection synced from the Console returns to `ok`. This is the only check that proves the key
  opens the vault; the two above it prove the gateway is running.
- The exported file parses as JSON, and `manifest.connections` lists the connections you expect.
- Console → The ledger carries a row under the tool `export`, and one under `erase` if you ran one,
  each with the scope it was given.

## What you have now

One archive, mode `0600`, holding a 32-byte key and a custom-format dump that only restore together
— and a restore you have actually run, or at least a checksum that says the two halves match. The
export is a separate thing: a readable JSON snapshot of the cached data, with no credentials in it,
no route that reads it back, and a shelf life that ends at the next sync.

What you are carrying from here. Scheduling and off-box copies are yours; the gateway ships neither,
and a backup that lives only on the machine it protects is not one. A key rotation re-seals the
whole vault, so every dump older than it needs the older key: take a fresh archive immediately
before rotating, and keep the pre-rotation one until every connection is green again. The archive is
as sensitive as the credentials it can open, because it
carries the key that opens them. And `docker compose down -v` still deletes the volume that holds
that key — with a current archive that is now a recoverable mistake instead of a permanent one,
which is the whole reason the archive exists.

If you erased, the rows are gone and the ledger says so. The connections and their credentials
survived, so a sync brings each source back — except a Plaid connection, whose Item was removed
upstream and needs a new Link.
