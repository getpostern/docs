description: "Entity states stream in over one authenticated socket, and an agent granted home runs the services you would run yourself. The one source that acts."

<Info>
  **Before you start**

  - **A running Home Assistant on your own network.** Postern reaches it directly, from the machine
    Postern runs on — there is no cloud relay in between and no account to create.
  - **About five minutes.**
  - **A long-lived access token**, created in Home Assistant in the first step below. It is shown
    once, at the moment it is created. Open your password manager before you start.
  - **The LAN address of the machine Home Assistant runs on** — an IP and a port. A `.local` name
    will not work here, and neither will `localhost`. The second step is finding it.
  - **Postern installed, with the Console in front of you.** The Console answers on the loopback
    address of the machine Postern runs on, so if that is a NAS or a home server, bring it to
    yourself first: [reach the Console over SSH](/start/remote-access#reach-the-console-over-ssh-when-it-runs-on-another-box).
  - **A Home Assistant account you are willing to lend.** The token carries exactly what that user
    can do, and Postern acts as that user — never as more.
  - **This connection acts, and does not only read.** An agent granted the `home` sector can
    dispatch any service on the catalog, with no per-action confirmation and nothing narrower than
    the sector to grant. Admin and system services are refused; everything else is yours to lend.
</Info>

<Steps>

<Step title="Create a long-lived token in Home Assistant" titleSize="h2" id="token">

In Home Assistant, open your profile — bottom-left in the sidebar — and scroll to **Long-lived
access tokens**.

<Warning>
  The token is shown once, at the moment it is created, and nothing re-reveals it afterwards. There
  is no way back to it, only a new one. Copy it into your password manager before you leave that
  dialog, and keep it there: you paste it into the Console in the last step of this page, and again
  every time you have to reconnect.
</Warning>

Create the token and name it `Postern`. The name is for you — it is what you look for in this list
on the day you want Postern's access to stop. The token appears in full, once, and it carries
exactly what your own Home Assistant user can do.

</Step>

<Step title="Find the LAN address of the Home Assistant machine" titleSize="h2" id="address">

Write down the address of the machine Home Assistant runs on: its IP on your network, and the port
Home Assistant answers on there. The Console's own example of the whole thing is
`http://192.168.1.50:8123`. What you write down has that shape:

```text
http://<ha-lan-ip>:8123
```

Postern dials that address from inside its own container, not from your browser, and the two do not
resolve names the same way.

<Warning>
  A `.local` name that works in your browser does not work here: mDNS does not resolve from inside a
  container. Neither does `localhost` or `127.0.0.1` — inside the container those name the container
  itself rather than the machine, even when Home Assistant is running on that same machine. Nothing
  rejects a wrong-but-well-formed address at the moment you paste it: the Console accepts it, the
  connection is created, and the stream then never comes up. Use the LAN IP, and give the Home
  Assistant machine a static lease so it stays true.
</Warning>

</Step>

<Step title="Paste the address and the token into the Console" titleSize="h2" id="paste">

Console → **Sources** → **Add a source** → **Home Assistant**. The card asks for two values:
**Instance URL** takes the address from the last step, and **Long-lived token** takes the token from
the first. The scheme is not optional — the Console checks the shape before it spends a round trip,
and a bare host comes back as *"That isn’t a URL — your Home Assistant address starts with http://
or https://, e.g. http://192.168.1.50:8123."*

Press **Connect Home Assistant**. A message reads *"Home Assistant connected."*, the Console returns
to Sources, and the new connection appears under home carrying the badge **Awaiting first push**.

That badge is expected, and it does not clear the instant it appears. Postern opens the socket from
a scan of its own connection table that runs every 60 seconds, so a connection made now starts
streaming within about a minute — no restart, and nothing for you to press. When it does, the badge
goes away, because a healthy connection carries none, and the connection reads **Instant —
connected** instead.

<Note>
  The connection reads **Unreachable**, with *"can't reach source — retrying"*: nothing answered at
  that address. Postern keeps trying, backing off from five seconds to a minute and staying there,
  so a Home Assistant that was merely still booting comes good on its own. A wrong address never
  does — check it against the warning above, then paste the corrected one here.
</Note>

<Note>
  The connection reads **Error**, with *"auth failed: invalid token"*: Home Assistant refused the
  token. Postern does not retry that one, deliberately — Home Assistant throttles repeated
  authentication failures, so a bad token is treated as terminal and no timer will bring it back.
  Paste a new token on this same card. It says *"Home Assistant is already connected. Connecting
  again replaces the stored credential — it won’t create a second copy."*, you tick **Yes — replace
  the stored credential**, and the button reads **Reconnect Home Assistant**. The next scan sees the
  changed credential and starts the connection over within a minute. The same path repairs a wrong
  address.
</Note>

</Step>

</Steps>

## Confirm it works

These five prove the socket is open, the cache is filling, and an agent can find something to do.
The first four are in the Console; the last one needs an agent you have already granted `home`.

- Console → **Sources**: the Home Assistant connection carries no badge at all, and reads **Instant
  — connected**.
- Open that connection. Under **Live stream**, the words **Stream down** are absent, and the line
  beneath reads *last event* with a time on it rather than *no events yet*.
- The same screen counts what it holds: **Entities cached** with a number on it, and **Stream**
  reading **live**.
- Change something in Home Assistant — a light, a switch — and that *last event* time drops back to
  seconds ago. That is the open socket, not a poll; there is no cadence to tune anywhere in this
  connection.
- Ask an agent granted `home` what it can do in the house. The catalog comes back with ids of the
  form `home.<domain>.<service>` — `home.light.turn_on`, `home.lock.lock`. An empty catalog means
  the socket is not up, because the catalog is served from the live connection's cache and from
  nowhere else.

## What you have now

The home sector, reading and acting. Any agent you have granted `home` sees entity states, browses
the service catalog, and dispatches the services you would use yourself — lights, scenes, switches,
scripts, automations and buttons are all one kind of thing to Home Assistant, and all of them are on
the catalog. Postern computes which services apply to which entity, which Home Assistant will not
tell you, and serves that join from cache, so discovery costs an agent no round trip to your house.

What it can never do, by construction, is touch an admin or system service. The `hassio`, `update`
and `backup` domains, `homeassistant.restart` and `homeassistant.stop`, and every `reload` are
dropped from the catalog and refused again at dispatch, so naming one directly does not get around
the omission: the answer is `admin/system service not permitted (device/entity control only)`.

The permission has one shape and it is the sector. A granted sector covers reading and acting
together; there is no narrower grant, no per-action tier, and no confirmation step between an
agent's decision and your house. Your instruction to the agent is the authorization, the grant is
what bounds it, and Console → **The ledger** is what records it: every call lands there under that
agent's own name, `invoke_action` among them, and the ledger only appends.

Each dispatch is sent once and never re-sent. If the connection breaks mid-call Postern reports
`unknown — not retried` rather than trying again, because it cannot know whether Home Assistant
acted before the wire went, and a second send could act twice on a real device.

What you are carrying from here is one standing credential. The token sits sealed in Postern's vault
on your own machine, and it stays exactly as powerful as the Home Assistant user who made it — if
that account gains permissions, so does this connection. Revoke the token in Home Assistant and the
socket dies at its next authentication with *auth failed: invalid token*, and the connection stays
in error until you paste a new one. Take it away from the Postern side instead — the connection's
own screen has **Remove token** — and, in the Console's words, *"Deletes the long-lived token from
the vault. Home stops immediately."*

One asymmetry to keep in mind when the socket is down: entity reads keep answering from the cache
Postern already holds, while the catalog and dispatch do not, because both are served from the live
connection. An agent can still say what the house was, and cannot change it.
