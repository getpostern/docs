*your own Google Cloud app + one app password · about 20 minutes · weekly re-consent until you publish to production*

<Note>
  **BEFORE YOU BEGIN** — Gmail never rides the OAuth app — by design, not
  omission. Moving Gmail onto the Gmail API would trigger Google's annual CASA
  security assessment for every self-hosted deployment, so mail is IMAP on
  purpose: the Google app below requests no Gmail scope, ever, and a test
  enforces it.
</Note>

## Part A · Gmail {#part-a}

### 1 · Turn on 2-Step Verification first {#two-step-verification}

The App-passwords page does not exist until 2-Step Verification is on — no
amount of searching the Security page will surface it before that.
[myaccount.google.com](https://myaccount.google.com) → Security → 2-Step
Verification → turn it on. Then come back here.

### 2 · Create the app password, paste it with your address {#app-password}

Go directly to the address below, create a password named "Postern", then
Console → Sources → Gmail → your address + the 16 characters. Paste them however
you like — the whitespace is stripped before sealing. Mail bodies are never
stored; only envelopes are cached, and content is fetched on demand.

```
myaccount.google.com/apppasswords
```

## Part B · Calendar & contacts — the consent screen comes first {#part-b}

### 1 · Create one project, and stay in it {#project}

At [console.cloud.google.com](https://console.cloud.google.com) open the project
picker at the top of the page → New project — everything in this Part happens
inside that ONE project.

### 2 · Enable the two data APIs {#enable-apis}

First enable the two data APIs: APIs & Services → Library → search "Google
Calendar API" → Enable, then "People API" → Enable.

<Warning>
  **TRAP** — A 403 on calendar or contacts right after a successful sign-in
  means the APIs are not enabled in the project that owns your client — the most
  common post-consent failure, and the error will not say so. And mind the
  Library search: contacts data comes through the People API — the
  similarly-named legacy "Contacts API" is deprecated, appears first when you
  search "contacts", and enabling it does nothing. Enable the right two in that
  project's Library, give Google a minute or two to start honouring it, then
  Reconnect in the Console.
</Warning>

### 3 · Configure the consent screen {#consent-screen}

Then configure the consent screen — the modern console names it Google Auth
Platform → Audience — audience External, app name and contact emails. Internal
is only offered to Workspace organizations.

### 4 · Add yourself as a test user {#test-users}

Test users → add your own address. This is the step that blocks the whole flow
if skipped.

```
console.cloud.google.com → Google Auth Platform → Audience → Test users → Add users
```

<Warning>
  **TRAP** — Skip the test-users step and Google refuses your own consent with:
  "OAuth access is restricted to the test users listed on your OAuth consent
  screen." While the app's status is Testing, only listed accounts may consent —
  and a fresh app starts with nobody listed, not even you.
</Warning>

### 5 · Create the OAuth client — type Web application {#oauth-client}

Google Auth Platform → Clients → Create client → application type Web
application. Under "Authorized redirect URIs" — not the JavaScript-origins list
above it — add the URI pasted from your own Console's Google card. Never typed,
and never copied from this page: Google exact-matches the string, and the
Console's copy follows your gateway's own port. On a stock install it reads as
below. Then copy both the client ID and the client secret: Google is a
confidential client here, and the token exchange fails without both.

```
http://localhost:8787/api/oauth/google/callback
```

<Warning>
  **TRAP** — Google shows the client secret once, at creation. Copy the client
  ID and the secret from the confirmation dialog before you close it: a lost
  secret cannot be re-revealed. The only way back is deleting the client and
  creating a new one — and the old client id dies with it.
</Warning>

### 6 · Paste both into the Console, sign in — and expect the warning {#console-card}

Console → Sources → Google → client ID + client secret → "Save & sign in with
Google" — and sign in as the account you listed under Test users; any other
account is refused.

<Note>
  One more clock: the consent window is 10 minutes and single-use — wander off
  mid-flow (say, to go add your test user) and the stale tab fails; start again
  from the Console card, nothing is lost.
</Note>

### 7 · Continue past the warning, then tick "Select all" {#consent-run}

A Testing-status app shows Google's "unverified app" interstitial — Continue is
the small link on the left; the prominent blue button is "Back to safety" and it
aborts. On the scopes screen the checkboxes start EMPTY: tick "Select all", or
continuing will "succeed" while granting nothing. Approve, and the one consent
fans out into two connections: calendar and contacts.

## Confirm before you move on {#confirm}

- 2-Step Verification is on — without it the App-passwords page does not exist.
- The Console's Gmail card holds your address and the sixteen characters.
- In the one project that owns your client: Google Calendar API and People API
  both read Enabled — and the service name is not `contacts.googleapis.com`.
- On Google Auth Platform → Audience: your own address is listed under Test
  users.
- On Google Auth Platform → Clients: a Web application client whose Authorized
  redirect URIs — not JavaScript origins — holds the URI copied from your
  Console's Google card.
- Both the client ID and the client secret sit in the Console's Google card.
  Google is a confidential client; one without the other fails the exchange.
- Every scope box was ticked before you approved.
- Three connections: Gmail, calendar, contacts.

## What stands when you finish {#what-stands}

Three connections in all — Gmail over IMAP from Part A, calendar and contacts
from Part B — and any agent granted those sectors answers from them after the
first sync. One standing cost until you act on it: while the Cloud project's
publishing status stays "Testing", Google expires Part B's refresh tokens every
7 days and you re-consent weekly. Setting the status to "In production" — the
Publish app button on the same Google Auth Platform → Audience page where you
added Test users; a form, not a review, for a single-user app you own — ends it.
